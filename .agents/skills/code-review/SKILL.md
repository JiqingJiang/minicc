# Code Review

在适用测试完成后，对本轮实际代码差异做独立审查。Review 回答“实现是否可靠且易维护”，测试回答“所检查的行为是否通过”。不要把 Review 和产品用户验收混为一谈。

## 1. 锁定审查范围

- 阅读已确认的目标、实施说明、验收条件和相关模块文档。
- 检查当前工作区状态、任务基线差异、暂存与未暂存变更和未跟踪文件；区分本轮工作与先前未提交的修改。
- 沿变更调用路径阅读必要的相邻代码、接口和测试。对照实际实现，不因计划或文档声称正确就跳过检查。
- 参考项目规则和相关历史决定。发现已有问题时，标明它是否由本轮引入或放大。

## 2. 审查重点

1. **正确性与风险**：错误条件、边界值、并发/生命周期状态、权限检查、异常传播、资源清理和潜在数据丢失。
2. **回归与契约**：调用方、序列化格式、公开接口、默认行为和既有功能是否受影响；错误是否可恢复。
3. **模块职责与封装**：相关状态和不变量是否有明确所有者；重复行为是否应由同一抽象维护；跨层职责是否放错位置。
4. **重复与复杂度**：重复代码是否会产生行为漂移；是否引入没有稳定变化理由的过度通用层、无用包装或配置；实现是否比需求需要的更绕。
5. **测试质量**：关键正常路径和失败路径是否覆盖；断言是否验证行为；是否有漏测、脆弱测试或测试通过但关键场景未覆盖的问题。
6. **方案一致性**：实现是否符合用户确认的逻辑、取舍、范围和已接受限制。

只有存在具体维护成本或行为风险时才建议抽象/封装。不要仅凭文件长度或个人风格偏好要求拆分，也不要把无关历史债务纳入本轮重构。

## 3. 输出问题

先列出可行动的问题，按严重性排序。每条包括：

- 严重性：`P1` 高风险，`P2` 应修复，`P3` 可改进；仅将确实阻断使用的问题标为 `P0`。
- 文件与行号，或精确代码路径。
- 触发条件、实际影响和证据。
- 建议的修复方向（不强行指定唯一实现）。

避免只写“可能有 bug”“需要更好封装”等不可验证判断。没有发现问题时，说明审查覆盖范围和未能判断的部分，不宣称整个系统无缺陷。

## 4. 发现后的处理

Code Review 默认只审查并报告，不自行编辑。若本轮已授权范围明确包含修复，可在报告后修复并重新运行相关测试与 Review；否则将问题交给用户决定。若修复改变已确认的行为、接口、数据格式、依赖或架构取舍，先回到 [开发流程](../develop-change/SKILL.md) 对齐方案。

审查完成后进入 [开发流程的用户验收与版本交付阶段](../develop-change/SKILL.md#用户验收与版本交付)。
