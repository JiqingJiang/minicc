# 开发流程

## 1. 对齐最终目标和本轮结果

读[项目目标](../../../docs/project-goal.md)。用户第一次给出明确的最终目标时，当场记录其原意。有待澄清的标准就标明待确认。如果新想法与已确认目标冲突，指出差异并请用户决定是否更新目标。

每轮开头用几句话说清最终目标、本轮推进的结果和验收方式。只收到最终目标时，先找最值得验证的模块或假设，提出一个能体验的切片供讨论。

## 2. 深入讨论与留痕

- **查现状。** 读[模块文档](../../../docs/modules/README.md)、相关 Note 和必要的实现。明确用户遇到的问题、出现条件、现有行为和限制。把事实、假设与未知分开。
- **比较现实选项。** 说明方案如何工作、覆盖什么、主要成本和风险。可包含维持现状或先做小验证。用实际参考的项目、文档、实例或实验说明依据，并标出仍待验证的假设。探索性实验若需要改代码或配置，按当前范围取得实现授权。
- **说透取舍。** 给出倾向方案、接受了什么代价、放弃了什么、为什么，以及哪些新证据会改变决定。提前讨论如何让用户亲自体验、怎样测正确性、评测要回答什么问题。
- **随讨论记录。** 把用户的新想法、有复用价值的讨论更新到[对应 Note](../../notes/README.md)。保留动机、参考、选项、选择和理由。讨论仍开放时保留在 `proposed/`，写出待确认问题；已有同主题记录就更新。实现细节进入对应模块文档。

## 3. 用户同意后整理 Spec

用户明确要求或同意把本轮方案写成 spec 时，在对应模块目录编写 `spec.md`。写清本轮结果、范围、行为与接口、约束和假设、体验步骤、功能验收、评测场景与标准。未决定的事项标出来，并链接相关 Note。

讨论可以跨多轮。会话结束、用户认可方向或 Agent 给出建议都不触发 spec。用户授权整理 spec 时仅做该动作，除非同一指令也明确启动实现。

## 4. 用户明确开始后实现

收到对当前范围的明确实现指令后，核对目标、验收和待确认项。依[模型分工](../model-routing.md)给 Luna 可独立验证的实现切片，说明可改范围、应保留的行为及回报要求。主 Agent 处理跨模块取舍、看实际改动并复核整合结果。

实质扩大范围或改变已确认行为时，回到讨论并等用户授权。完成后更新模块文档中的当前实现、运行和体验步骤，再进入[验收流程](../review-change/SKILL.md)。Note 的状态随对应结果更新。
