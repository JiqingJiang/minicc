# 模型分工与任务派发

开始重要任务时，从客户端可用的模型中为主会话选择 GPT-6.2-Sol。已开的会话以客户端显示为准。必要时用 Sol 承担高难判断，并由主 Agent 整合。根据客户端或派发记录核实实际模型。

## 默认分工

- 主 Agent 负责理解目标、选择方案、处理歧义，以及涉及架构、跨模块依赖、公共接口、数据格式、用户可见行为和不可逆取舍的工作。优先使用 GPT-6.2-Sol。当前环境没有该模型时，使用可用的强模型并在交付中说明实际模型。
- Luna 负责边界清楚的动手工作，例如指定文件内的实现、局部修复、测试补充、格式整理和验证。派发时必须写明目标、文件或目录边界、不得触碰的范围、验收条件和回报格式。
- 主 Agent 保留最终的方案判断、跨文件整合、冲突处理和交付前复查。Luna 的结果必须经过主 Agent 检查，不能把子任务完成当成整体完成。

## 何时派发

涉及代码、测试或配置的派发，沿用[根规则](../../AGENTS.md#授权与执行)下本轮已授权的实现范围。

适合派发的任务具备独立文件或模块边界，能够用明确的验收条件判断结果，并且不需要子 Agent 临场决定产品方向。代码量很小的改动直接完成，派发成本高于执行成本时不要拆分。

只有在各部分能够独立验证且没有共享写入时才并行派发。多个任务会改同一文件、同一接口或同一决策时，由主 Agent 顺序处理，先解决取舍再动手。派发前先检查已有改动和目标路径的写入权限。各任务需要共享写入时可改为顺序交接。

## 派发格式

```text
目标：完成什么可观察结果
范围：允许修改的文件或目录
边界：不得修改的文件、接口或行为
验收：需要运行的检查与通过标准
回报：改了什么、运行了什么、结果怎样、剩余风险
```

Codex 提供 `luna_worker` 时优先使用该角色。客户端仅支持指定子 Agent 模型时，显式选择可用的 Luna。委派不可用时，由主 Agent 顺序完成并说明实际分工。无法确认模型时，在交付中说明。

## 接收结果

主 Agent 核对改动范围、实际差异和子任务证据。产品的用户体验与正式验证由主 Agent 统一交接。若 Luna 发现需求歧义、共享边界冲突或需要新取舍，应暂停该部分并把具体问题、影响和待选方案交回主 Agent，不要自行扩大范围。

完成实现后按[评审与交付流程](review-change/SKILL.md)复查。

参考 [Codex 子 Agent 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)。
