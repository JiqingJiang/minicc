# 项目文档整理

用于用户要求归档已讨论或已实现的 MiniCC 模块设计与过程时。先按项目授权规则确认哪些文档被要求更新；用户明确要求整理模块时，可直接更新指定范围内的文档，不改产品代码。

## 权威位置

- 当前有效、用户已确认的需求和行为约束：`docs/specs/<模块名>.md`。
- 实际模块设计、当前实现逻辑、接口边界、运行方式、验证证据和已知限制：`docs/modules/<模块名>.md`。
- 影响未来范围、方案、接口、约束或验收的原因与取舍，以及需要复查的问题根因、Code Review 发现和修复结论：`.agents/notes/<状态>/<类别>/YYYY-MM-DD-主题.md`。

## 整理原则

1. 阅读当前代码、spec、测试、相关模块文档、协作规则和已有 Agent Notes。将确认的目标、实现事实、测试事实和历史推断分开；不得把实现细节倒推成用户确认的 spec。
2. 先更新同主题权威文档，再移除已被合并取代的重复或过期草稿。历史评测只有在其版本、条件或未决结果会影响后续决策时才保留，并明确标注时效和局限。
3. 模块文档说明模块为何这样组织、关键路径如何工作、边界和失败行为如何落实。将过程提炼成稳定解释，不按时间线复述聊天或复制代码。
4. Agent Notes 只写以后可能改变决策的关键取舍、问题根因、修复结果、证据和重议条件。普通实现事实留在模块文档；一次性尝试和已有测试已充分表达的细节不另记。
5. 在 spec、模块文档与 Notes 间建立反向可达的链接；修正文档索引和所有受影响的内部链接。全文搜索旧路径，避免留下失效引用。
6. 复核文档和实际实现、验证结果及当前未完成验收是否一致。需要跨会话保留的证据写明版本或工作区基线、命令、结果和空缺。
