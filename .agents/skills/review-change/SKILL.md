# 验收与版本交付

## 1. 交给用户先体验

对照本轮目标和 spec 或已确认条件审阅改动。记录待验证的代码快照，例如当前基线及改动范围、已有提交号或可复查的快照标识。提供前置条件、启动入口、典型输入和体验重点，必要时把本地运行入口准备好。

交接时明确当前阶段，等待用户亲自运行并反馈后开展正式功能测试。用户报告体验问题时，联系原目标与预期行为记录。需要改代码时回到[开发流程](../develop-change/SKILL.md)，等用户明确授权。改动影响体验路径时，再交给用户复体验相关部分。

## 2. Agent 做功能测试

对用户体验的同一版本运行功能测试。测试前记录版本和相关改动，检查测试工作区是否混入无关变更。尚无提交时可使用可复查的工作区快照。测试期间出现影响结果的相关改动时，重新确认基线并重跑受影响的用例。

把每条验收条件对应到观察结果。优先从真实入口验证主路径、关键失败路径、边界和受影响的回归。记录运行命令、输入或前置条件、预期、实际结果和跳过原因。将结果标为通过、失败或未验证。

## 3. 深度评测

从本轮目标和讨论中的风险选评测问题。按模块选择有代表性的场景，例如结果质量、性能、稳定性、恢复、资源消耗或兼容性。记录场景和样本、版本、运行环境、度量方法和基线或阈值（如已建立）。功能测试结果决定哪些场景有有效基线。遇到失败时注明受阻部分，继续能独立执行的评测。

把需要跨会话复查的功能与评测结果记到[对应模块目录](../../../docs/modules/README.md)。向用户交付功能结论、深度评测结论、限制和下一轮可讨论的改进。把有意义的改进和取舍更新到 [Agent Notes](../../notes/README.md)，经过验收的想法移入 `implemented/`；明确暂存或否决的依记录规则迁移。

## 4. 提醒保存版本，由用户授权

本轮验收后，提醒用户可以保存版本，说明建议提交范围、当前分支、验证版本和远程目标（如存在）。明确说明仍有失败或未覆盖的项。只有用户授权提交才暂存本轮文件并提交。只有用户授权推送才推送。用户明确要求「提交并推送这一版」时，两步均可执行。

提交信息由 Agent 根据本轮实际改动起草，格式为 `<英文类型>: <中文摘要>`。按主要改动选前缀，例如 `feat: 新增命令行入口`、`fix: 修复空输入处理`、`docs: 补充模块运行说明`、`chore: 更新开发配置`。摘要用简短中文说明实际变化，必要的命令和代码名称可保留原文。

执行前核对待提交内容、实际测试的代码与目标分支。保留无关改动。缺少仓库、远程或目标分支有歧义时说明实际阻塞。推送后核对远程目标是否包含该提交，汇报提交号与目标分支。代码与验收快照发生实质差异时，先补齐受影响验证再交付版本。
