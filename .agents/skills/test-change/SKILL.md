# 测试流程

在实现完成后、Code Review 前调用。测试应回答本轮行为是否满足验收条件及主要失败路径是否受控。不要把测试数量或“企业级”标签当作质量证明；根据风险、边界和用户场景选择检查。

## 1. 确定本轮变更范围

1. 阅读本轮已确认的目标、实施说明和验收条件。
2. 检查 `git status`、相对任务基线的 `git diff`、暂存差异，以及新增未跟踪文件。使用 `git log` 或 blame 理解背景，但不能只根据 commit 选择测试。
3. 将当前任务修改与已有未提交改动分开。若无法区分，明确标出覆盖范围和归因限制；不得把其他改动误认为本轮交付。
4. 查看受影响代码、既有测试、模块说明及真实验证入口。先确定要保护的行为，再选测试。

## 2. 选择测试层级

- **单元测试**：纯逻辑、状态转换、校验、边界值和错误分支可独立验证时采用。
- **集成测试**：模块间契约、适配器、持久化、工具执行或权限协作受到影响时采用。
- **功能或端到端测试**：真实入口上的关键用户流程、交互或任务生命周期受到影响时采用。
- **回归测试**：缺陷修复应覆盖原故障条件，防止同一问题再次出现。

并非每项改动都需要所有层级。说明所选层级与风险的关系，以及为何跳过其他层级。先查项目已有运行方式，不凭空编造命令或预期结果。

## 3. 尽可能先定义失败条件

对有清晰、可观察验收行为的功能或缺陷，优先先写能暴露问题的最小测试，确认它在旧行为下失败，再做实现并确认通过。对难以隔离、成本不合理或需要真实服务的场景，可先通过既有集成/功能入口验证；说明先测后写不适用的原因。不要为了追求 TDD 形式引入脆弱测试或测试专用的生产抽象。

修改测试的授权应包含在本轮实现范围内。新增测试应验证外部行为或稳定契约，避免把实现细节锁死。

## 4. 执行与报告

运行选择的检查，并在可行时运行受影响范围内的回归检查。报告：

- 检查命令或人工操作、对应层级与覆盖行为。
- 实际结果；失败时保留错误事实和是否由本轮变更导致的证据。
- 未运行的检查、原因和风险。
- 工作区基线限制、外部依赖或无法复现的部分。

绝不声称没有运行的测试通过。测试流程结束后，将实际变更和结果交给 [Code Review](../code-review/SKILL.md)。产品用户体验与深度评测按 [开发流程的收尾阶段](../develop-change/SKILL.md#用户验收与版本交付) 进行。
