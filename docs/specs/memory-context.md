# MiniCC Memory 与 Context 模块 Spec

状态：用户已确认按《Agent Memory 模块设计：从写入到检索》重做 Memory 设计。实现事实见[Memory 与 Context 模块说明](../modules/memory-context.md)，方案取舍见[决策记录](../decisions/implemented/architecture/2026-11-22-memory-context-storage.md)。

模块职责和代码边界见[架构与代码目录](../architecture.md)。当前 Agent Loop 与 Session 的实际实现见[Agent Loop 模块说明](../modules/agent-loop.md)。

## 目标与术语

- **Memory** 保存可跨聊天复用、可由用户纠正的偏好和事实。
- **Context** 在每次模型请求前，选择并组装完成当前任务所需的信息。
- 会话历史是交互记录；任务状态是当前任务目标、已确认决定、计划与进度；两者都不自动等于 Memory。
- Context 可以从 Memory 取材，但 Memory 不负责决定每次请求如何装配上下文。

## 目标行为

1. 新聊天能用上相关且有效的长期偏好；用户可查看、纠正、删除，或在当前聊天覆盖偏好。
2. 重开会话或任务时，Context 能带回已确认目标、决定、进度与待解决事项，并按需引用会话原文和产物。
3. 每次模型请求的上下文来源可追溯，并记录预算使用、裁剪、检索和压缩情况。
4. 当前用户明确要求优先于一般偏好；当前任务已确认的要求优先于不适用的历史信息。

## Memory 模块要求

Memory 是跨时间复用经验的上下文管理机制，核心分为写入与检索。会话历史保存原始证据，Memory 保存经筛选、带来源、可修正的长期记录；指令、任务状态和项目文件仍是独立来源。

### 记忆分类与范围

第一版支持以下类别：

| 类别 | 适合保存的内容 |
| --- | --- |
| `user_preference` | 稳定的表达、协作、工具或输出偏好。 |
| `user_correction` | 用户明确纠正且未来可能重复适用的做法。 |
| `project_fact` | 当前项目中无法稳定从文件推导、但后续任务需要的背景事实。 |
| `decision` | 已确认并可能影响未来工作的决定。 |
| `procedure` | 可在未来任务中复用的步骤或经验。 |
| `reference` | 有用的信息位置或检索线索，不复制无关的大段材料。 |

记忆范围分为全局和项目。全局只用于跨项目普遍适用的用户偏好；项目事实、项目决定和项目过程默认归属当前项目。Agent 可提出范围，存储层负责将其隔离到对应命名空间；语义不确定时不得扩大为全局。项目身份按 Git 根目录规范化绝对路径计算，非 Git 工作区按其绝对路径计算。

每条记忆至少包含稳定 ID、原子化内容、类别、范围、来源类型与引用、关键词/实体线索、创建/更新时间、有效状态和关联记录。应能区分用户明确指示、用户纠正、已确认决定、Agent 提取和用户编辑；会话来源关联 session 与 turn。有效时间和关系用于表达更新、冲突与历史状态。

### 写入流程与关系处理

- Agent 在正常对话中判断长期价值并通过内部 `memory_remember` 工具写入，无需用户逐条新增或批准。用户明确提出“以后记住”或长期纠正时优先写入；普通闲聊、临时任务要求、未经确认的猜测、可直接从当前项目文件获得的信息和敏感凭证不得保存。不得在会话结束后批量扫描整段旧历史。
- 写入内容应尽量原子化，一条记录表达一个可复用事实或偏好。工具参数包含类别、范围以及与旧记忆的关系提议；来源类型由运行时根据当前用户轮次判定，不接受模型自行声明为用户指示/纠正。来源保留 session/turn，取代操作还须由存储层校验可信来源标记。
- 重复：同范围、同类别、内容完全相同的记录不重复创建；语义重复可关联已有记录并合并来源证据。
- 补充：新增内容作为独立记录保存，并关联补充对象；不得覆盖原记录。
- 明确更正/取代：新增记录成为当前有效记录；旧记录标记为已取代并保留原内容、来源和时间。取代必须引用同范围内的旧记录；只有明确用户纠正/指示可取代长期偏好，已确认的项目决定也可被新的明确决定取代。
- 时间变化：记录新旧事实各自的有效时间；旧事实保留为历史，不再作为当前事实检索。未提供生效时间时使用记录时间。
- 冲突或无法确定：保留两侧记录并标记冲突组，检索时作为一组呈现，不允许静默覆盖或只返回其中一侧。需要决定未来行为且证据不足时，Agent 可向用户简短澄清。
- 程序必须校验关系目标存在、未删除且属于同范围；关系转换只改变状态并追加来源，不得物理覆盖历史。精确重复由程序拦截。用户可显式解决冲突、编辑或删除记忆。
- 写入拒绝疑似密码、API key、token 等敏感值；记忆作为不可信参考内容，不得获得指令或工具权限。

### 检索流程

- Memory 提供 Agent 可调用的 `memory_search` 工具；Context 同时在模型请求前自动执行一次有界召回，避免 Agent 因忘记调用搜索工具而漏掉明显相关的稳定偏好。Agent 可在自动召回不足时调用工具搜索更具体或历史信息。
- 查询意图从当前用户请求和必要的当前任务目标构造，不只依赖单一最新句子的字面词。先按全局及当前项目过滤，再按类别、有效状态和时间意图选候选，禁止跨项目检索。
- 基础检索使用 BM25 关键词排序、jieba 搜索模式中文分词、字段关键词/实体命中和短语匹配；同时用本地轻量 embedding 计算语义相似度并与词法分数组合。语义模型不可用或推理失败时退化到本地关键词检索，不阻塞写入和会话。记忆内容不得为向量化发送到远程服务。低相关结果不注入。
- 只注入超过相关度门槛且在条数与 Token 预算内的少量记忆。冲突组须共同呈现并标记未解决状态。被取代记录只在历史/时间问题中按需检索；删除记录绝不检索。
- 搜索结果和 Context trace 记录 ID、范围、类别、状态、分数、命中理由和来源引用，不记录完整记忆正文到 trace。注入内容应标明为不可信参考，不能覆盖当前用户要求、任务确认、项目指令或项目中可核验的当前事实。

### 用户管理

用户可查看、搜索、检查历史/冲突、编辑、解决冲突和删除。界面不要求用户手动新增。编辑保留旧版本和来源；删除后不再进入搜索或 Context。`/memory` 默认作用于当前项目；全局记忆需要显式指定 `global`。

## Memory 与 Context 的接口

Memory 负责原子记录、范围隔离、关系状态、存储和相关候选检索；Context 负责结合当前请求/任务，从候选中排序、限额并组成模型输入。Memory 不把整库内容默认放入请求。当前用户要求、已确认任务状态、指令和项目文件优先于长期记忆；项目记忆优先于同样相关的全局偏好。

## Context 模块要求

### 输入来源

Context 根据当前请求，从以下来源选择信息：

- 当前 Agent Profile 对应的 System Prompt；
- 当前用户消息及本轮已收集的澄清回答；
- 当前任务的目标、确认要求、计划、进度、决定和待解决事项；
- 当前会话的近期消息，以及按需引用的原始会话或任务产物；
- 相关的全局/项目指令与适用规则；
- 按当前请求选出的 Skill 说明；
- Memory 返回的相关候选；
- 当前请求可用的工具定义；
- 本轮已执行工具的必要结果与证据。

来源需要有清晰边界：会话保存对话，任务保存任务状态，Memory 保存跨任务信息，Context 生成单次模型请求视图。工具执行器和 Agent Loop 仍各自拥有工具权限与调用循环职责。

### 指令发现与优先级

- System Prompt 按当前 `agent_id` 选择对应 Agent Profile；默认 Agent 必须有默认 Profile。不同 SubAgent/Team 成员可配置不同名称、职责和 System Prompt。未注册的 `agent_id` 必须明确报错，不能静默套用其他 Agent 的角色。
- Skill 通过可注入的 Provider 按当前请求和 `agent_id` 返回候选；Context 负责限制数量/内容预算、注入模型请求并记录来源。Skill 的发现、存储和用户管理由后续 Skill 模块负责。
- MiniCC 只自动发现名为 `MINICC.md` 的指令文件：全局文件位于 `~/.minicc/MINICC.md`，本地文件位于当前工作区根目录的 `MINICC.md`。先加载全局文件，再加载工作区文件；`AGENTS.md` 和嵌套目录中的 `MINICC.md` 不属于 MiniCC 默认加载的文件。发现路径、加载顺序、覆盖规则和单文件/总量上限必须确定且可检查。
- 同一来源不得重复注入；嵌套或按路径适用的规则仅在其适用范围内加载。
- 冲突时遵循：安全与系统边界 > 当前用户明确要求 > 当前任务已确认要求/决定 > 适用项目规则与本任务已选 Skill > 相关 Memory > 通用默认行为。若上层约束导致不能执行，应说明冲突，而非静默忽略。
- 指令内容是模型可见的行为指导，不替代权限执行边界。

### 选材、预算与延迟加载

- 每次请求有按模型窗口、输出预留和安全余量计算的输入 Token 预算；在确定模型请求前估算或读取可用 Token，并记录实际用量（若适配器可提供）。预算、压缩触发比例/目标、最近轮次保留数和单来源上限可配置。
- Context 为系统/项目指令、任务状态、会话历史、Memory、Skill/工具说明和工具结果分配预算；优先保留当前明确要求、任务状态和完成当前步骤所需证据。
- 超预算时按优先级裁剪或摘要，并记录被裁剪来源；不得静默丢弃用户确认的关键决定或未解决事项。
- 大文件、详细记忆、旧会话和完整工具输出默认不整份载入。先使用索引、摘要或有界检索，必要时再读取原文。
- 每次模型请求均可追溯来源、选取理由、估算/实际 Token 数、裁剪与摘要情况。

### 历史压缩与恢复

- 接近模型上下文上限时按完整用户轮次压缩较早历史，保持工具调用及结果配对；当前用户请求和不可丢失的任务状态不能因压缩删除。超长工具结果按预算裁剪，并保留原始会话证据供恢复。用户显式触发压缩可作为交互入口能力按需提供。
- 摘要至少保留当前任务目标、已确认要求与决定、关键进度、重要工具结果/证据、未解决问题和下一步。
- 压缩后保留原始会话记录或可恢复引用；摘要应能关联其覆盖的历史范围，不能伪装成原始用户消息。
- 任务状态、全局/项目指令及可检索 Memory 与对话摘要分层维护，不因压缩而丢失或相互覆盖。
- 恢复时以持久任务状态和原始证据校正摘要；若摘要与用户当前指令冲突，遵从当前指令。

### 子 Agent 上下文

若后续提供子 Agent，Context 按子任务目标传递完成工作所需的最小任务信息、适用指令和证据引用。默认不复制整个会话或全部 Memory。子 Agent 的新增事实或决定应带来源返回，由父任务判断是否写入任务状态或长期 Memory。

## 第一版范围

第一版按以下顺序交付：

1. Context 组装当前消息、任务状态、项目指令、有限会话历史和必要工具/工具结果；先实现来源追踪与基础预算记录。
2. Agent 按策略自动写入全局/项目记忆；用户可查看、搜索、编辑和删除；Context 只注入少量相关记忆。
3. 支持保留原始历史的压缩与恢复，验证已确认任务信息不会因压缩丢失。
4. 用真实任务评估自动记忆的准确性、遗漏和错误写入，以及连续性、用户介入、Token 和耗时，再调整写入策略。

首版 Context 预算由模型窗口、输出预留和安全余量计算，并将压缩触发比例、压缩目标、近期轮次数、Skill 和工具结果上限做成可配置项。当前默认值及实际压缩方式见[模块实现说明](../modules/memory-context.md)，后续可依据真实任务评估调整。

## 暂缓决定

以下事项不在第一版预先定为产品行为，需基于真实任务另行讨论确认：

- 是否回溯扫描旧聊天补充记忆；当前不自动回扫历史。
- 自动冲突合并、重要性评分、过期判定和记忆遗忘策略。
- 跨项目共享、跨设备同步、备份与导入/导出。
- 检索重排或其他复杂检索方案。
- 基于真实任务调整 Context 各来源的 Token 分配比例和压缩阈值；是否引入模型生成式摘要。
- 子 Agent Memory 独立存储及长期记忆的写权限。

## 验收标准

### Memory

- 全局与项目记忆能分别创建、查找、编辑、纠正和删除；项目间不会意外串用。
- 明确要求记住的信息在新聊天可按相关性查到；无关记忆不进入请求上下文。
- 删除或作废的记忆不会继续注入；冲突记录能展示来源和时间，用户当前明确要求可覆盖本次任务。
- 敏感凭证不会被写入 Memory。

### Context

- 请求仅包含当前任务所需的指令、任务状态、会话历史、Memory、工具说明及结果；当前要求与来源优先级符合本 Spec。
- 大型历史或资料能按需查阅，不会无边界装入单次请求。
- 模拟或执行预算超限时，可观察到裁剪/摘要和来源记录；关键任务要求与待办在压缩后仍可恢复。
- 对单次请求能检查装配来源及用量记录；恢复任务后能区分权威任务状态、摘要和原始会话证据。

产品实现后应按项目开发流程完成适用测试、独立 Code Review、用户体验验收和真实任务评测。具体测试计划和结果写入模块实现说明，不在本 Spec 中虚报为已完成。
