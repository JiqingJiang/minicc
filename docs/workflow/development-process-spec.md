# MiniCC Codex 协作流程设计

状态：迁移进行中。项目决策记录和 Codex 配置骨架已落地；插件触发、自动化流程及完整体验仍待新会话和真实开发任务验收。

## 背景与目标

当前开发过程存在三类问题：零散想法容易直接变成实现任务；文档沉淀频繁但缺乏长期价值；用户主要描述目标时，Agent 可能未经充分说明就选定实现方式，导致逻辑、质量和维护性难以掌控。

本流程要让 Agent 自主完成调研、实现和验证，同时让用户在是否值得做、重要方案取舍及实现逻辑上保有清晰的决策权。工作流应减少无效文档和用户阅读代码的负担，并提升代码正确性与可维护性。

## 范围

- 覆盖从零散想法、方案分析、实现授权，到测试、代码审查和交付的项目协作过程。
- 规定何时比较外部方案、何时创建或更新模块文档和项目决策记录。
- 定义测试与 Code Review 的职责边界，以及它们如何使用实际变更范围。
- 本仓库以 Codex 为唯一项目协作入口；不维护 Claude Code 的规则副本或兼容入口。
- 本流程只约束项目协作，不改变 MiniCC 产品运行时支持的模型或工具。

## Codex 文件职责

- 根目录 `AGENTS.md` 只保存 Codex 每次工作都要遵守的 MiniCC 规则，并链接到细化流程。
- `.codex/config.toml` 管项目级 Codex 设置；本项目当前启用个人已安装的 `superpowers@openai-curated` 插件。插件代码留在个人 Codex 环境中，不复制进仓库。
- `.codex/rules/*.rules` 是 Codex 原生的命令执行许可配置，用于沙箱外命令的允许/询问/拒绝策略；它不是通用项目规范目录。跨任务的自然语言约束放在 `docs/rules/`，由 `AGENTS.md` 自动读取的规则索引引导按任务加载。
- 通用规划、测试、调试和审查工作流由外部插件提供。项目规则、spec/模块/决策文档所有权以及实现授权仍由 `AGENTS.md` 和 `docs/` 决定。
- `.codex/hooks.json` 与 `.codex/scripts/` 是后续机械化检查的落点。本轮只搭配置骨架，不添加自动测试或文档校验；先确认触发条件、耗时和失败反馈，再启用具体 Hook。
- 项目决定统一保存在 `docs/decisions/`，不放在 Codex 配置或个人插件目录中。
- 不维护仓库级 `.agents/skills/` 副本。个人插件的安装不随仓库分发；其他使用者需在自己的 Codex 环境安装插件并信任本仓库，项目配置才会生效。
- 不保留 `CLAUDE.md` 或其他 Claude Code 专属协作规则副本。产品目标、模型清单或技术比较中提到 Claude 不属于协作入口，不因此删除。

## 工作阶段与交接条件

### 1. 想法探索

用户可以在此阶段自由提出未成形的想法。Agent 将其整理为待解决的问题、目标用户或使用场景、预期收益、主要未知项，以及最低成本的验证方式；在证据有限时，说明继续探索、做小实验、暂缓或放弃的利弊。

本阶段默认不改产品代码、不创建项目文档，也不把每个想法当成已批准需求。只有用户决定推进后，才进入方案设计。跨对话保存未决想法的方式暂未确定；在确定之前，不自动新增想法文档。

### 2. 方案设计与决策

Agent 先检查当前实现、相关项目规则、现有模块文档和已确认决定。若改动涉及新模块、架构边界、重要依赖或用户可见行为，应调研可比方案，优先使用一手资料，并解释其适用条件、代价及与 MiniCC 现状的关系。局部、低风险改动可简化调研。

进入实现前，Agent 提供一份短小、可审阅的实施说明，至少包含：

- 目标行为和范围，包括明确不做的事项。
- 用户可理解的核心执行逻辑、重要边界和失败行为。
- 主要模块或接口变化及其归属理由。
- 候选方案、选择理由、关键权衡与已接受的限制。
- 计划修改的主要路径和验证方式。
- 仍需用户决定的问题。

对会实质改变交付行为、公共接口、数据格式、安全边界或依赖的选择，Agent 应暂停并向用户说明选项及影响。常规、低风险的实现细节可在已确认范围内自行决定。

模块当前 spec 的路径为 `docs/specs/<模块名>.md`。已有 spec 时应更新同一份文件，不因每轮讨论创建新文档。模块实际设计和实现说明归 `docs/modules/<模块名>.md`。方案获得用户确认后，按项目授权规则进入实现；Spec 的编写和批准本身不授予产品代码修改权限。

### 3. 实现

Agent 按已确认范围实施。实现中若出现会改变目标行为、方案核心取舍、接口、依赖或授权范围的新决定，应暂停相关部分并交用户选择；不应静默扩大范围。

开始验证前，Agent 根据当前工作区差异确定本轮实际变更范围。检查应覆盖相对任务基线的已跟踪差异、暂存与未暂存修改，以及新增未跟踪文件；Git 历史用于理解背景和先例，不单独作为变更清单。已有未提交工作须与本轮工作区分，避免遗漏或错误归因。

### 4. 测试

测试以用户可观察的验收行为为起点，并根据风险和受影响边界选择层级：

- 单元测试：适用于可独立验证的业务逻辑、状态转换、边界条件和错误处理。
- 集成测试：适用于模块、存储、模型适配或工具之间的交互契约。
- 端到端或功能测试：适用于从真实入口贯穿关键用户流程的场景。
- 回归测试：针对已修复的问题或易重复出现的缺陷保留检查。

不是每项改动都必须覆盖所有层级。Superpowers 的测试工作流可协助实现阶段的验证，但具体测试范围仍根据差异和影响选择，并说明选择理由、实际结果及未覆盖部分。对有明确可观察行为的改动，尽可能先写能暴露问题的测试，再实现并确认测试通过；若测试先行不适用，应说明原因。不能把未经执行的测试写成已通过，也不能笼统声称“企业级测试”而不列具体范围和证据。

### 5. Code Review

Code Review 是对本轮实际差异的独立质量检查，至少关注：

- 正确性、边界条件、异常路径和潜在回归。
- 模块职责、接口边界、必要的封装与抽象。
- 重复逻辑、冗余代码、无用复杂度和过度设计。
- 测试是否覆盖关键行为，是否存在脆弱或误导性断言。
- 与已确认方案、架构规则和现有实现的一致性。

审查结果先按严重性列出具体问题、位置、影响和依据。审查发现不能静默扩展成无边界重构；修复须在当前授权范围内，实质改变行为或方案时重新交用户决定。测试负责验证行为，Code Review 负责判断实现质量，两者互补；外部插件可以协助，但不能替代用户验收。

### 6. 验收与交付

按开发流程的用户验收与版本交付阶段进行用户体验、功能验证和深度评测。交付摘要应让不读完整代码的用户也能理解：

- 实际交付的行为与主要逻辑。
- 核心方案和权衡，以及为何这样实现。
- 改动落在哪些模块，模块职责如何保持清晰。
- 跑过的验证、结果、未覆盖项和已知限制。
- 与确认范围的偏差（若有）及待决定事项。

提交与推送分别需要用户明确授权。Git 提交标题使用中文描述，可保留 `feat:`、`fix:`、`docs:` 等类型前缀；提交前核对暂存范围并对照近期历史格式。

## 文档所有权与沉淀门槛

文档写入应遵循单一主要来源，其他文件通过链接引用，避免重复维护：

| 信息 | 权威位置 | 沉淀条件 |
| --- | --- | --- |
| 项目长期目标与范围 | `docs/goal.md` | 用户要求改变长期目标时再更新；该文件当前已定稿。 |
| 当前模块设计、实际行为、边界、运行和验证方式 | `docs/modules/<模块名>.md` | 实现改变了可持续复用的模块事实、接口或验证入口。 |
| 当前有效的模块 spec | `docs/specs/<模块名>.md` | 用户明确要求或同意写 spec；同一模块持续更新，完成后标明状态并链接实现证据。 |
| 持续有效的项目规则 | `docs/rules/<主题>.md` | Codex 每项相关任务都需要遵守的跨任务约束；根 `AGENTS.md` 引导按任务主题读取。 |
| 重要理由、取舍、问题根因与 Review 处置 | `docs/decisions/<状态>/<类别>/YYYY-MM-DD-主题.md` | 记录具体决定的原因和重议条件，不保存持续规范或规则副本。 |
| 测试与评测证据 | 对应模块文档或已有验收记录 | 记录可复查命令、版本、结果、未覆盖项；真实任务比较质量、介入、耗时和 Token 时保留所需数据。 |

讨论和实现中的重要决定在用户确认后，由 Agent 主动记录到正确的权威位置；无需用户另行要求记录。一次对话可以产生零条或多条记录。持续规范更新到 `docs/rules/`；具体决策按上述条件记录在 `docs/decisions/`。普通进度、临时尝试、已经有权威来源的事实、没有后续影响的选择和未证实的推测不写入文档。新增记录前先查找并更新已有主题文档，避免一轮对话新建一个文件。

## 可复用工作流与自动化

- Superpowers 插件为个人 Codex 提供通用的方案规划、测试驱动开发、调试、并行工作和代码审查流程；MiniCC 不再维护这些通用 Skill 的副本。
- `AGENTS.md` 作为项目级规则入口，保留 MiniCC 特有的探索/实现授权边界、文档归属、验收与 Git 授权。
- `docs/workflow/codex-setup.md` 说明插件安装范围、项目设置和 Hook 自动化边界；`docs/decisions/README.md` 管理项目决策记录。
- 自动测试或文档检查暂不由 Hook 触发。后续先用真实任务确认哪项检查重复、可确定、失败可清楚反馈，再在 `.codex/hooks.json` 中配置并通过 Codex 的 Hook 信任流程验收。
- 用户体验、完整功能验证、真实任务评测和交付由主 Agent 按本流程负责；外部插件不能替代这些 MiniCC 专属验收要求。

## 用户体验验收

使用一个真实的、范围尚未完全明确的改动，验证以下情形：

1. 用户抛出零散想法时，Agent 先协助判断问题和价值，不擅自开始实现或生成零散文档。
2. 决定推进一个需要方案选择的模块改动时，Agent 先检查现状并提供可理解的实现逻辑、方案比较和取舍，等用户确认重要选择后再实施。
3. 实施后，Agent 根据真实差异选择测试层级，运行测试并报告确切证据；Code Review 能指出真实的正确性、抽象或重复问题，而不是只给泛泛评价。
4. 交付说明让用户无需逐行读代码，也能复述核心逻辑、关键取舍、验证结果和剩余限制。
5. 只有对后续工作有实质影响的决定和实现事实进入已有模块文档或项目决策记录；普通过程不产生新文档。

## 未决事项

- 未决想法是否需要跨聊天保存，以及后续是否出现足够稳定的需求来建立机会清单。
- 不同风险级别是否需要比会话确认更显式的方案批准记录。
- 哪些测试或 Code Review 失败应成为阻止交付的硬门槛，需由真实任务经验确定。
- 重大改动调研需要达到的深度和证据数量，需结合实际任务调整，不预设统一数量。
